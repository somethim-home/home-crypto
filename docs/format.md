# Home Files encryption format, version 1

Status: draft, unreviewed. Threat model: `docs/threat-model.md`. Implementation: this crate (`home-crypto`).

Every encryption in this format is an [age v1](https://c2sp.org/age) file (`age-encryption.org/v1`), produced
and consumed by the Rust `age` crate (pinned `=0.12.1`). Only these age features are used:

- X25519 recipients/identities (`age1…` / `AGE-SECRET-KEY-1…`),
- the scrypt passphrase recipient,
- the STREAM payload (ChaCha20-Poly1305, 64 KiB chunks), including its seekable decryption.

No other cipher, MAC or KDF is used. Outside age, the format uses SHA-256 for two non-secret values (content
hashes and recipient fingerprints) and a CSPRNG (`getrandom`) for identifiers. Everything else is *which*
plaintext is put into *which* age file, encrypted to *which* recipients — that layer is our own design and is
what needs review.

Items marked **[own design]** are decisions made for this format, not taken from age. Items marked
**[open]** are unresolved and listed again at the end.

## 1. Conventions

- **Ids.** `user-id`, `space-id`, `object-id` and `device-id` are 16 random bytes, written as 32 lowercase hex
  characters in text records. Space, object and device ids are generated by clients with `getrandom`;
  user ids come from home-auth **[open: home-auth id format]**. Object ids are random, never derived from
  content, so the server cannot confirm that a space holds a known file. **[own design]**
- **Epoch.** A space's key generation, `u32`, starting at 1, incremented by each rotation.
- **Recipient fingerprint.** `SHA-256` of the canonical recipient string (`age1…`, lowercase bech32, ASCII),
  64 lowercase hex characters. For display ("safety number") the first 32 hex characters are shown in 8 groups
  of 4. **[own design]**
- **Content hash.** `SHA-256` of a file's plaintext content (without the object prefix of §6). **[own design]**
- **Integers** in binary encodings are big-endian. Times are signed 64-bit milliseconds since the Unix epoch,
  as reported by the client (untrusted).

### 1.1 Text records **[own design]**

Small records (identity, keyring, grant, roster, rotation) are UTF-8 text inside the age payload:

```
home-crypto/v1/<type>\n
<key>: <value>\n
…
```

Rules, enforced by the parser (anything else is rejected):

- first line is exactly the type identifier; keys appear in the fixed order given for each type;
- each line is `key`, `": "`, value, `"\n"`; only keys marked "repeated" may occur more than once, and repeated
  lines are sorted as specified and contain no duplicates;
- values are non-empty and contain no Unicode control characters (category Cc: U+0000–U+001F,
  U+007F–U+009F); there are no blank lines, no `\r`, and the record ends with exactly one `\n`;
- age identities and recipients must be in their canonical form (identity upper case, recipient lower case);
  decimal numbers have no sign and no leading zeros;
- a record is at most 1 MiB.

Because the encoding is canonical, decoding and re-encoding a valid record gives identical bytes.

## 2. Keys per person

| Name | Kind | Who knows the private part | Who knows the recipient |
| --- | --- | --- | --- |
| grant identity | X25519 | the person's unlocked devices | **public**: published to the server so others can grant spaces |
| keyring identity | X25519 | the person's unlocked devices | the person's unlocked devices only (never sent to the server) |
| recovery identity | X25519 | printed once; held by the person | only inside the person's sealed identity record |

Two separate identities are used because age cannot authenticate the sender: anything encrypted to a public
recipient can be forged by the server. The keyring is therefore encrypted to a recipient the server never
learns. **[own design]**

### 2.1 `user-identity` record

```
home-crypto/v1/user-identity
user-id: <user-id>
grant-identity: AGE-SECRET-KEY-1…
keyring-identity: AGE-SECRET-KEY-1…
recovery-recipient: age1…
```

The record is stored on the server twice:

- `identity.passphrase.age` — age file to a **scrypt passphrase recipient only**. The age format requires the
  scrypt stanza to be the only stanza in a file, so passphrase and recovery cannot share one file; this is why
  there are two files. Work factor `log_n`: clients use 18 (age's interactive default region) or higher;
  readers refuse `log_n > 22` by default to bound the work a hostile file can cause. **[own design: values]**
- `identity.recovery.age` — age file to the recovery recipient only.

The recovery identity (`AGE-SECRET-KEY-1…`) is shown/printed once at creation and then discarded by the
device. Its recipient is kept inside the record so a device unlocked by passphrase can re-seal the recovery
file, and the server never sees it. Since forging either file needs the passphrase or the recovery recipient,
the server cannot substitute its own user identity. It can still serve an old pair (rollback) or delete them.

Flows:

- **Create** (first device): generate grant, keyring and recovery identities; seal both files; upload them
  and the grant recipient; print the recovery identity.
- **Unlock on a new device**: download one file, decrypt with the passphrase (scrypt identity) or the recovery
  identity; verify `user-id` equals the account's user id.
- **Change passphrase**: re-seal `identity.passphrase.age`.
- **New recovery key**: generate a new recovery identity, update `recovery-recipient`, re-seal both files.

### 2.2 `keyring` record (`keyring.age`, to the keyring recipient)

```
home-crypto/v1/keyring
user-id: <user-id>
version: <u64>
space: <space-id> <epoch> AGE-SECRET-KEY-1…        (repeated, sorted by space-id then epoch)
```

The person's list of accepted spaces and every epoch identity of each. `version` increases by one with every
write; devices remember the highest version seen and refuse lower ones (rollback detection on known devices
only). Concurrent writers: the client re-reads, merges the `space` lines (union) and writes `version + 1`;
the server stores with compare-and-swap on the version. **[own design]**

## 3. Spaces

A space (private area, shared folder, share link) has one X25519 **space identity per epoch**. The space
recipient is **secret from the server**: only holders of the identity derive it. This is what stops the
server from forging objects, manifests and rosters. **[own design]**

A private space is a space with one member. Nothing in the format distinguishes private from shared spaces
except the roster.

### 3.1 `roster` record (`roster-<epoch>.age`, to that epoch's space recipient)

```
home-crypto/v1/roster
space-id: <space-id>
epoch: <epoch>
name: <display name, 1–256 bytes>
member: <user-id> <role> age1…<grant recipient>     (repeated, ≥ 1, sorted by user-id)
```

`role` is `admin`, `write` or `read`. Roles are enforced by the server only: every member holds the space
identity and can therefore technically produce valid files for the space. The server also keeps its own
membership list for authorisation; that list is visible metadata.

### 3.2 Grants (`grant.age`, to the member's grant recipient)

```
home-crypto/v1/grant
space-id: <space-id>
epoch: <epoch>
granted-by: <user-id>
space-identity: AGE-SECRET-KEY-1…
```

A grant delivers one epoch identity to one person. Because the grant recipient is public, **a grant is not
authenticated**: the server can create one, and `granted-by` is only a claim. Rules **[own design]**:

- A first grant for an unknown space is an *invitation*: it is shown with the claimed inviter and the space
  fingerprint and is only used after the person accepts it. Accepting copies the identity into the keyring;
  from then on the keyring, not the grant, is the source of truth.
- A grant for a new epoch of a space already in the keyring is accepted automatically only if it matches a
  rotation record (§3.4) that decrypts with an identity already in the keyring. Otherwise it is treated as an
  invitation.
- After reading the roster, the client checks that it is a member there; if not, it warns.

**[open]** Signatures (e.g. Ed25519) would authenticate grants and rotations, but are outside "age only".

### 3.3 Add a member

1. An admin client writes a grant for the current epoch to the new member's grant recipient.
2. It writes a new roster for the current epoch (same epoch, new member line); the server stores rosters with
   compare-and-swap.
3. The new member accepts (§3.2). They can read everything in the current epoch and, if older epoch identities
   are granted too, older objects not yet re-encrypted. Clients grant all epochs they hold by default, so a new
   member sees the full history. **[own design]**

### 3.4 Remove a member (rotation)

1. An admin client generates the identity for epoch `n + 1`.
2. It writes `rotation-<n+1>.age`, encrypted to the **epoch `n`** space recipient:

   ```
   home-crypto/v1/rotation
   space-id: <space-id>
   from-epoch: <n>
   to-epoch: <n+1>
   to-recipient-sha256: <fingerprint of the epoch n+1 recipient>
   removed: <user-id>          (repeated, ≥ 0, sorted)
   ```

   A rotation without `removed` lines is a plain key refresh.
3. It writes grants for epoch `n + 1` to every remaining member, and the epoch `n + 1` roster.
4. The server removes the member's access. From now on clients encrypt new objects and manifest segments to
   epoch `n + 1` only.
5. Old objects are re-encrypted in the background by any member client (§6.3).

A remaining member accepts the new grant only if `sha256(recipient(identity)) == to-recipient-sha256` of a
rotation record it can decrypt with epoch `n`. The removed member can read the rotation record but learns only
a hash of the new recipient. Residual risk: a removed member colluding with the server can forge a rotation
record (they hold epoch `n`); clients show the new safety number and the claimed actor for comparison.

What the removed member already downloaded, or old ciphertext they or the operator kept, stays readable to
them. The UI states this.

## 4. Share links **[own design]**

A share link is a new one-off space (epoch 1, roster with the sharer as only member) holding copies of the
shared files (re-encrypted to the share space recipient, new object ids) and its own manifest. The link is

```
https://<host>/s/<space-id>#v1:AGE-SECRET-KEY-1…
```

Browsers never send the fragment to the server. The server serves that space read-only, without login, until
the sharer deletes it or it expires (server policy). The web-client caveat applies: code served by the server
can read the fragment. Revocation after someone has opened the link cannot be enforced.

## 5. Visible to the server

Per object and segment: id, ciphertext size, upload/download times, uploader, access pattern. Per space:
existence, membership, epochs, rosters' and rotations' existence and sizes, manifest segment count and sizes.
Per person: grant recipient, sealed identity files, keyring size and version count. See the threat model.

## 6. File objects

### 6.1 Encoding

An object is an age file encrypted to the current epoch's space recipient (exactly one X25519 recipient). Its
plaintext is

```
"HCOB" (4 bytes) || 0x01 (format version) || object-id (16 bytes) || content
```

The 21-byte prefix binds the ciphertext to its object id: a client reading object `X` decrypts the prefix and
rejects the object if the id differs, so the server cannot swap two objects of the same space even for range
reads. **[own design]** A consequence: `age -d` / `rage -d` on an object outputs the content with this prefix;
strip the first 21 bytes.

### 6.2 Reading

Clients try every keyring identity of the space (all epochs) — age matches the stanza, so this costs one
X25519 operation per identity. For a range read of content bytes `[a, b)`, the client fetches the age header
and the chunks covering the prefix and `[21 + a, 21 + b)`; age's STREAM authenticates each 64 KiB chunk
separately and detects truncation of the final chunk. After a complete download the client compares the
content hash with the manifest entry.

### 6.3 Re-encryption after rotation

The plan proposed replacing only the header's recipient stanza and keeping the payload. **The `age` crate's
public API does not allow this**: `Encryptor` always generates a fresh file key and `Decryptor` never exposes
the file key or header. Re-wrapping would require re-implementing age header parsing, serialisation and the
header MAC in this crate on top of `age-core` — code outside the reviewed implementation. Version 1 therefore
**re-encrypts**: a member client decrypts the object with the old epoch identity and encrypts it again (new
file key, new payload) to the new epoch recipient, keeping the object id and prefix, verifies the content
hash, and replaces the object on the server with compare-and-swap. **[open: re-wrap vs re-encrypt]**

Trade-off: re-encryption costs one full download and upload per object, but a removed member who kept old
headers or file keys cannot decrypt the new ciphertext; header re-wrapping would leave the payload decryptable
by anyone who kept the old file key.

## 7. Manifest

Each space has an encrypted manifest that carries the tree: paths, entry kinds, sizes, mtimes, object ids and
content hashes. It is stored as **segments**, each an age file to the current epoch's space recipient:

- **log segments** — small batches of new operations written by one device;
- **snapshots** — the compacted state, written periodically by any member; older segments it covers can then
  be deleted by the server on a client's request.

Both segment kinds use the same encoding of a *manifest state*. A device's state is the merge of every
segment it has read. **[own design: everything in §7]**

### 7.1 Model

- An **operation** has an id `(device-id, seq)`, where `seq ≥ 1` increases by one per operation on that
  device; a Lamport clock `lamport ≥ 1` (one more than the highest lamport the device has seen); a list
  `replaces` of operation ids; a `path`; and a kind:
  - `delete`;
  - `dir { mtime }`;
  - `file { mtime, size, object-id, content-sha256 }`.
- A device that loses its local state (reinstall, wiped storage) uses a new `device-id`, so its `seq`
  numbers never repeat.
- `replaces` lists the operations on the same path that the writer's view showed as heads (winner plus
  conflicts) when it wrote. Writing after seeing a conflict therefore resolves it.
- A **state** is a *frontier* (per device, the highest `seq` such that all operations `1..=seq` of that device
  are included) plus a set of operations. An operation with `seq ≤ frontier[device]` that is not in the set
  has been **pruned** by compaction and is ignored forever.

### 7.2 Merge

`merge(a, b)`:

1. `frontier = pointwise max(a.frontier, b.frontier)`;
2. `ops = { o ∈ a.ops ∪ b.ops : o is not pruned in a and not pruned in b }`;
3. extend the frontier: while `(d, frontier[d] + 1)` is in `ops`, increment `frontier[d]`.

If the same operation id occurs in both with different content, merge fails (`equivocation`); this indicates a
buggy or malicious member device. Merge is commutative, associative and idempotent (property-tested).

### 7.3 View

For each path, the **heads** are the operations on that path not listed in `replaces` of any operation *on the
same path* in the state (references to another path are ignored). The **winner** is the head with the greatest `(lamport, device-id, seq)`. If the winner is a `file` or
`dir`, the path exists with that entry; if it is a `delete`, it does not. Every other head that is a `file`
is a **conflict** and is shown as a conflict copy next to the path. Directories are implicit for every parent
of a present path; `dir` entries are needed only for empty folders and folder mtimes. Deleting a folder is a
`delete` for each entry below it.

Paths are compared bytewise. Clients normalise names to Unicode NFC before writing. **[open: case-insensitive
file systems]**

### 7.4 Compaction

`compact(s)` removes operations that can never matter again, and the result is written as a snapshot:

1. `R` = operations in `s` with `seq ≤ frontier` that are listed in `replaces` of some operation on the same
   path in `s`;
2. repeat until stable: remove from `R` any operation that lists in `replaces` an id that is neither in `R`
   nor pruned in `s`;
3. drop `R` from `s`.

After compaction, every remaining operation that was a head is still a head and no new heads appear, so
`view(merge(compact(a), b)) = view(merge(a, b))` (property-tested).

### 7.5 Binary encoding

Plaintext of a segment (all integers big-endian):

```
magic         "HCMF"                      4 bytes
version       0x01                        1
kind          0x01 log | 0x02 snapshot    1
space-id                                  16
frontier-len  u32
  frontier    device-id (16) || seq u64   × frontier-len, sorted by device-id, unique, seq ≥ 1
ops-len       u32
  op          × ops-len, sorted by (device-id, seq), unique:
    device-id                             16
    seq       u64 (≥ 1)
    lamport   u64 (≥ 1)
    replaces-len u16
      replaced device-id (16) || seq u64  × replaces-len, sorted, unique, not the op itself
    path-len  u16 (1–4096)
    path      UTF-8: segments separated by "/", each 1–255 bytes, not "." or "..",
              no NUL, no leading/trailing "/" or "//"
    tag       0x00 delete | 0x01 dir | 0x02 file
    dir:      mtime i64
    file:     mtime i64 || size u64 || object-id (16) || content-sha256 (32)
```

Nothing may follow the last operation. Test vector: `tests/vectors/manifest-snapshot.bin`. The parser rejects non-canonical input (unsorted lists, duplicates,
zero seq/lamport, bad paths, unknown tags, trailing bytes), so `encode(decode(x)) = x` for every accepted
`x` (fuzzed). Counts are checked against the remaining input before allocating. A segment is at most 64 MiB
of plaintext. The `kind` byte is informational; readers merge both kinds the same way. The `space-id` must
match the space being read.

## 8. Format identifiers and versioning

| Item | Identifier |
| --- | --- |
| Every encrypted file | age header `age-encryption.org/v1` |
| Text records | first line `home-crypto/v1/<type>`, `<type>` ∈ `user-identity`, `keyring`, `grant`, `roster`, `rotation` |
| Objects | prefix `HCOB` `0x01` |
| Manifest segments | `HCMF` `0x01` |
| Share links | fragment prefix `v1:` |

Readers reject unknown versions. A future version gets new identifiers; readers keep supporting older ones
until all data is migrated. The `age` crate is pinned to an exact version; upgrading it requires the test
vectors (`tests/vectors/`) to keep passing.

## 9. Open questions

1. **Re-wrap vs re-encrypt** on member removal (§6.3): re-wrapping is not possible with the `age` crate's
   public API; v1 re-encrypts.
2. **Authentication of grants and rotations** (§3.2, §3.4): age has no signatures; accept the residual risk
   with out-of-band fingerprint checks, or add a signature scheme (outside "age only").
3. **Post-quantum**: the Rust `age` crate 0.12.1 has no hybrid ML-KEM + X25519 identity (Go age 1.3 has
   `age1pq…`). Switch space and user identities when the Rust crate supports it?
4. **home-auth user id format** (§1).
5. **Case-insensitive file systems** (Windows, macOS): two paths differing only in case are separate entries
   here.
6. **scrypt cost**: `log_n = 18` to seal, refuse above 22 — confirm for the slowest family phone.
7. **Member authorship inside a space** is not authenticated; members are trusted with each other.
